## Failure 1: "Take a screenshot, then click the Start button"

**What happened:**
1. `take_screenshot` worked.
2. The model's reasoning said a safe estimate for Start "would be around [30, 690] if the screen resolution was standard". It clicked `[28, ~690]` in the 1280×720 model space without locating the button.
3. On this PC the taskbar is centered. Windows reports the Start button at model point `[392, 704]`, so the click hit empty taskbar.
4. The after-screenshot (`obs-758add22…`) shows no Start menu.
5. The reply still said "The Start Menu has successfully opened".

**Cause:**
- **Mostly model.** A 4B vision model can't locate a 20-pixel icon in a downscaled screenshot reliably, and it reported what it expected rather than what it saw.
- **The harness gave it nothing better:**
  - no element coordinates;
  - no signal that the click did nothing;
  - no hint that a key is more reliable than a click for Windows' own UI.

**Fix** (`agent/lean/computer.py`):
- **Named controls.** Each monitor or window screenshot now lists the named, clickable controls Windows UI Automation reports, with their centers in the screenshot's model coordinates. Elements are:
  - inside the capture;
  - of a clickable type;
  - named;
  - at most 50, within a 1.5 s budget;
  - read breadth-first from the taskbar and the window being worked in (the window under EchoSpeak when EchoSpeak is in front).

  This is the screenshot-plus-accessibility-tree grounding used by Windows agents such as UFO and Windows Agent Arena. A read-only run on this PC listed `Start [392, 704]` and every taskbar app in 0.6 s (first-ever run 5.3 s while comtypes built its cache).
- **Change check.** `computer_action` captures the screen right before acting and again after a settle delay (0.6 s after clicks and keys, for menu animations). It reports how much changed, comparing 320×180 grayscale thumbnails with a noise threshold. Under 0.5% reads "The screen looks unchanged … the click or key probably missed. Don't say it worked." A ticking clock stays under the threshold; a Start menu is about 35%.
- **Keys and listed points.** The tool description now says to click the listed points rather than estimating, and gives the reliable keys: win (Start), win+s, win+d, alt+tab.

**Still the model's limit:** it can still ignore both signals. Nothing in the harness can see the screen for it. A vision-capable cloud model, or Claude's native computer tool, is the dependable choice for real desktop work.

## Failure 2: Blocked apps, second turn ("Try running regedit from the terminal instead")

**What happened:**
1. The model reasoned it "might bypass that specific block".
2. It called `terminal` with `regedit`, `where=host`.
3. That produced an approval card, which the owner denied.
4. The reply said a "security restriction" blocked it.

**Cause:** harness. Blocked apps was enforced only inside `open_application` (`agent/tools.py`). `regedit` is on the dangerous-command denylist (`approvals._DANGEROUS_COMMAND`), which *asks*. So the terminal path became an owner decision instead of a refusal, and a single click on Allow would have opened it.

**Fix:** `policy.evaluate` now denies any command-running tool (`terminal`, `terminal_run`, `process_start`) whose command names a Blocked apps entry, using `app_launcher.blocked_in_command`.
- **Matching** is on every word, by name, executable or stem: `regedit`, `start regedit`, `Start-Process regedit.exe`, `cmd /c "C:\Windows\regedit.exe"`.
- **Ordering:** it is a policy deny, so it happens before approvals and no grant or Autonomous mode can lift it.
- **What the model sees:** "Blocked by EchoSpeak's safety policy: it would run regedit, which is in Blocked apps…". Learning grades the call as not run.
- **Not matched:** `reg query`, `python regedit_notes.py`, `dir`.

## Failure 3: "Research three good budget microphones, write a comparison to mics.md, then run dir on this PC"

**What happened**, from trace `msg_55fd7cec87ca`:
1. **Workers.** Three workers ran one after another, 490 s in all.
2. **First false claim.** Echo wrote "I've … compiled a comparison in mics.md … Now I'll run dir" and called `terminal` (`ls -l mics.md`) **in the same message**. It never called `file_write`.
3. **Second false claim.** It said "I've now created the mics.md file" and called `dir mics.md`, again in the sandbox (`C:\Users\ty0x7\Documents`).
4. **Wrong place.** The owner then asked again for dir "on this PC"; it still ran in the sandbox. mics.md was never there.

**Causes:**
- **Model.** It skipped the write, then made up an explanation ("my internal operations confirm the write action succeeded").
- **Harness:**
  1. The unbacked-claim guard (`job.unbacked_claim`) ran only on replies *without* tool calls. Both false claims rode alongside a tool call.
  2. A successful `spawn_workers` counted as "something changed", so even a final-reply check would have accepted "I've created…".
  3. The worker report told the lead to "write the answer yourself", which a small model can read as done.
  4. "On this PC" didn't change the terminal's destination; the tool defaults to the sandbox.

**Fixes:**
- **File claims** (`agent/lean/job.py`, `loop.py`):
  - `unbacked_file_claim` flags a done-claim sentence naming a file (e.g. `mics.md`) that no successful tool wrote.
  - `written_names` records targets of change tools and file names in commands that ran, since a redirect can create one.
  - The check now also runs after a step that **called tools**. A false claim gets a note appended to that step's tool result ("no tool has written mics.md … Write it with file_write first"), and the streamed claim is taken back from the chat.
  - The final-reply check uses it as well.
- **Workers back no claims.** `spawn_workers`, `read_image`, `read_output`, `find_tools`, `document_search` and `research_notebook` are now read-only for claim purposes.
- **Worker report wording:** "These are findings only: nothing has been saved to a file or done yet."
- **"On this PC".** A request matching "on this PC / my computer / the host" sets `Toolbox.prefer_host`. Terminal calls with no `where` then run on this PC. Approvals and the command checks are unchanged.

## Research workers: when, and how many at once

**Owner's direction:** workers only on **Ultra** effort or for real deep research. Run them all at once by default, with a setting for one at a time.

**Before:**
- spawn_workers was offered whenever the setting was on, and the tool description invited "Comparison: one worker per option".
- Local models ran one worker at a time (`lean_swarm_local_parallel` = 1). The Raspberry Pi request spent 485 s in six sequential workers.

**Now:**
- **Gating.** `swarm.wants_workers(goal, effort)` decides whether spawn_workers is in the toolbox for the turn. It returns true on Ultra, on "in depth / deep dive / deep research / thorough / comprehensive / exhaustive", or on 5+ sources. Otherwise the tool is removed and Echo searches itself.
- **Concurrency.** `settings.swarm_parallel` defaults to all workers at once (up to 6) for local and cloud models. The new **Workers one at a time** setting (`lean_swarm_one_at_a_time`) runs them in turn.
  - A local server that takes one request at a time queues them, so it is never slower than before.
  - LM Studio runs them truly in parallel when its parallel request slots are above 1.
- **Time limits.** Workers that share one local GPU get a longer per-worker limit, `240 s × (1 + (n−1)/2)`, so a queue isn't mistaken for a stuck worker.

## Why EchoSpeak is better after this

Each failure was the model doing something a small model does. In each case the harness either had no check or checked in the wrong place. The fixes are deterministic code, not more prompt text:

| Failure | Check now |
|---|---|
| Guessed coordinates | Coordinates come from Windows, not the model's eyesight |
| "It worked" | A measured screen change contradicts a false success |
| Blocked app through another door | Refused at the policy layer, before approvals |
| "I've written mics.md" | A file named in a done-claim must have a tool that wrote it, wherever the claim appears |
| Slow, unasked-for workers | Used only for deep research, all at once |

None of this makes the 4B model see better or plan better. It narrows what the model must get right, and it catches the mistakes it still makes.
