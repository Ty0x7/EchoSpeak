# EchoSpeak model ecosystem and harness compatibility

Research snapshot: **2026-10-26 UTC**, expanded for all 20 explicit owner priorities. Implementation branch: `codex/model-compatibility-audit`, based on the pending 11.10.6 workbench. [Visual companion](../../artifacts/research/model-ecosystem.html) · [Structured catalog](model-ecosystem-catalog.json) · [Exact priority records](model-ecosystem-priorities.json) · [Download metadata](model-ecosystem-downloads.json) · [Existing Code integration record](echo-code.md).

## Outcome and evidence boundary

Echo already has a useful shared execution loop, provider-specific Claude/Live adapters, explicit session model selection, bounded tool recovery, and independent permission/privacy enforcement. Its biggest compatibility problems are protocol assumptions and context bookkeeping, rather than missing model names in a picker.

The initial change added stateless OpenAI Responses for GPT-6, current documented Claude effort controls, Gemini 4 Argon thinking recognition, configured context-window enforcement, retained catalog limits, and a correction for non-thinking Qwen3-Coder-Next. The expanded audit adds literal-only Liquid tool recovery, explicitly configured local reasoning replay/template toggles, a GLM-5.3 off-control correction, refusal of incomplete native tool streams, and exclusion of specialized Live/media models from ordinary Chat candidates. It does **not** add accounts for every provider surveyed or claim every open-weight family works with every runtime.

All model compatibility is **source-verified or conditional**, never live-certified in this investigation. No model was downloaded, no inference endpoint was called, no paid credits were used, and no performance benchmark was run. Mock HTTP streams and existing native-harness regression tests are the execution evidence. Existing 11.10.6 installers predate these compatibility changes; rebuild from this branch to include them.

## Reading the catalog

The catalog groups current families, still-relevant earlier weights, and specialist endpoints across 23 developers. It covers model authors separately from hosting services. This is a broad public ecosystem inventory, not a promise to enumerate every quant, fine-tune, restricted model or regional SKU. An official model card proves publication, not this account's entitlement or an installed runtime's support.

- **Confirmed contract:** inspected source plus targeted mocked behavior establishes a specific request/parsing property. This label never means real-model acceptance.
- **Conditional:** an Echo adapter exists, but exact ID, endpoint, template, account, configuration and live behavior still matter.
- **Unsupported:** the required native provider or specialized protocol is absent from Echo Chat.
- **Unverified:** evidence is insufficient to assert an end-to-end path, even if weights can be served over HTTP.

Numeric limits are cited examples, not a hardcoded operational capability registry. Catalog values do not overwrite settings or silently increase context allocation.

### Practical local selection

For lightweight on-device work, start acceptance with one familiar 4B–8B model; retrieval and a limited toolset matter more than a broad claim of agent competence. The 12B/20B group needs a larger allocation, while 24B–35B/MoE options generally require substantially more total memory than their active-parameter labels suggest. GPT-OSS 120B needs workstation/server-scale memory or offload. Maximum model-card context is never the default recommended allocation: first reserve output and runtime overhead, then set the actual server context and Echo's exact-model override consistently.

LFM2.5-24B-A2B and 8B-A1B are distinct checkpoints; the smaller one's official card calls it a reasoning model too, but does not establish identical controls. Nemotron Lightning uses template kwargs for a Boolean thinking switch; a native NVFP4 checkpoint cannot be substituted for a GGUF without a compatible engine. Gemma 12B Unified is encoder-free, while the 31B variant has different modality components. Avoid bulk-importing a collection of quantizations: choose one exact checkpoint/runtime contract for the owner's actual workload.

## Actual model-to-harness execution path

1. `apps/web/src/hooks/useProviderSettings.ts`, connected-model UI and settings routes discover candidates and store explicit selections. Favorites affect presentation, not API support. Catalog reachability and a generation test are separate actions; **this investigation did not invoke either against owner accounts**.
2. `agent/state.py` session bindings and `agent/core.py` select the native runtime. `agent/lean/runtime.py` resolves a persona's explicit provider/model, otherwise the session's model. Optional auto-routing is an explicit existing feature, not general error failover. Voice and vision paths retain additional selection constraints. Workers in `lean/swarm.py` inherit the lead's model and have bounded read-only tool/budget access.
3. `lean/prompt.py`, `soul.py`, `agent_skills.py`, project instructions, recall and memory-quality code construct the native prompt. Session history comes from the state timeline; recent visible exchanges and saved observation references are reconstructed, while older text can be summarized by `lean/summaries.py`.
4. `lean/provider.py` resolves the selected endpoint, hydrates up to three recent image observations, enforces configured text-only metadata, then checks privacy before network traffic. Missing keys and missing exact cloud model IDs fail clearly. Four direct cloud providers exist: OpenAI, Gemini, Anthropic and xAI. Local providers retain their separate base URL resolution.
5. Protocol dispatch now chooses **Responses for OpenAI GPT-6**, native Claude Messages, native Gemini Live, or compatible Chat Completions. The adapter translates the message/tool contract; it does not own permissions or execute tools. Responses requests use `store:false`, explicit non-strict versions of Echo's existing function schemas, and the selected reasoning effort.
6. `lean/loop.py` receives a canonical `ModelTurn`, preserves tool IDs and provider state, validates or repairs bounded argument syntax, and sends calls through `Toolbox`, approval policy, caller-role restrictions, project scope, taint/Rule-of-Two checks and stop handling. Unknown names get execution feedback; they do not become arbitrary callable functions. Model-generated tool syntax is never permission.
7. Native and recovered calls return canonical tool results to the same loop. Gemini `extra_content.google.thought_signature` and Claude signed/thinking blocks already survive tool cycles. New Responses output items retain opaque reasoning between steps only for the exact provider/base URL/model/credential fingerprint. Different accounts or models receive canonical visible history instead.
8. Content/reasoning deltas and tool events use existing SSE/timeline paths. Opaque Responses items stay in the current turn's working messages; they are not added to visible events, memories or the persistent chat timeline. A later user turn rebuilds visible history; this change does not introduce provider-hosted conversation storage.

The original **Codex app-server, Claude Agent SDK and ACP runtimes remain independent harnesses**, with their own sessions, tools, authentication and permissions. Their models are not interchangeable Echo provider entries. See the [Code architecture record](echo-code.md) for those integrations and worktree isolation.

## Corrections implemented

### OpenAI GPT-6 tool transport and state

Official [GPT-6 guidance](https://developers.openai.com/api/docs/guides/latest-model) distinguishes tool support by endpoint: Astra/6.1 Sol need Responses; Sol/Luna Chat Completions functions require reasoning off. Echo previously sent all of them through Chat Completions. `cloud_providers.chat_transport` now selects Responses for this family and reports that route in discovery metadata. Older families and compatible hosts keep their established transport.

`lean/responses_stream.py` adapts text/images and function-call outputs, forwards only Echo-provided tools, streams visible text/refusals and reasoning summaries, and maps token usage. It waits for terminal response output before returning function calls. Stream failure, missing completion and incomplete function turns raise a provider error; partial argument deltas cannot reach Toolbox.

[Stateless reasoning guidance](https://developers.openai.com/api/docs/guides/reasoning) requires retaining output items for continuation. They are scoped by provider, normalized base URL, model and credential fingerprint. They never use `previous_response_id`, remote stored history or a provider-side tool executor. Schema `strict:false` preserves Echo's optional parameters rather than silently making them required. The [function-calling contract](https://developers.openai.com/api/docs/guides/function-calling) is the reference for call IDs and returned items.

### Documented reasoning controls

Current Claude Fable 5.1 and Opus/Sonnet/Haiku 5.5 now map the effort picker to `output_config.effort`; exact documented families are recognized, with optional dated suffixes. Unknown releases keep provider defaults. The UI does not offer a universal thinking-off toggle. This follows the [Claude effort availability table](https://platform.claude.com/docs/en/build-with-claude/effort), rather than translating OpenAI parameters blindly.

Gemini 4 Argon now follows the documented [compatible reasoning mapping](https://ai.google.dev/gemini-api/docs/openai), with low effort when an off request cannot be honored. Existing 2.5/3 behavior and thought-signature round trips remain. OpenAI current high efforts map to native `xhigh`/`max` rather than all collapsing to `high`; Sol/Luna's documented `none` option is recognized.

Qwen3-Coder-Next no longer inherits the generic Qwen3 thinking heuristic. Its [official card](https://huggingface.co/Qwen/Qwen3-Coder-Next) explicitly describes a non-thinking model. Explicit owner metadata remains authoritative for a configured runtime; no speculative family-wide capability list was added.

### Context budgeting and discovery

`lean/settings.context_tokens(endpoint)` now uses the exact configured model profile, then a local model's configured context. A global trim setting can lower a known window, never enlarge it. Output reservations are bounded to half that window and the loop's usage display uses the same resolved budget. Unknown cloud limits retain a fallback and are not labeled physical limits. This corrects the previous minimum-64K assumption for a local allocation such as 4K/8K.

`cloud_providers._model_entry` retains positive provider-reported `inputTokenLimit`/`outputTokenLimit` as catalog metadata. It does not automatically load larger contexts, overwrite settings, or mark candidates live-validated. Existing model profiles remain the explicit source of runtime overrides.

## Expanded harness findings and GLM assessment

### Expanded compatibility corrections

The explicit Liquid priorities revealed an unhandled default wire representation. `lean/provider.extract_text_tool_calls` now recognizes complete `<|tool_call_start|>…<|tool_call_end|>` batches. The interior must be a list of named calls with keyword arguments containing literal JSON-compatible data. It uses Python AST parsing and `literal_eval`, **never eval/exec**, forbids positional/expanded/duplicate arguments and nested executable expressions, and rejects the whole malformed batch rather than executing its valid prefix. Recovered calls still enter the same registered Toolbox and approval gates. The [Liquid model card](https://huggingface.co/LiquidAI/LFM2.5-24B-A2B) documents this default call syntax. Hosts should still supply the correct template/reasoning parser, especially when a thinking prefix is already in the prompt.

Local compatible endpoints can now explicitly opt into `reasoning_history: "reasoning_content"` through the existing exact-model profile. Only the returned dedicated reasoning channel is retained—not inferred text tags. Continuation is limited to the same provider/base URL/model/credential fingerprint. Switching any of those, removing the profile opt-in, or using another transport strips this internal state. No raw reasoning field is forwarded globally. This supports the documented current-turn history requirement illustrated by [Laguna](https://huggingface.co/poolside/Laguna-XS-2.1) and [DeepSeek tool cycles](https://api-docs.deepseek.com/guides/thinking_mode/); it does not create their direct cloud account integrations or persistent external sessions.

`thinking_control: "chat_template"` is a separate explicit local profile option for servers that document `chat_template_kwargs.enable_thinking`. It maps the existing Think toggle to a Boolean and reports numeric effort unavailable, instead of mislabeling an OpenAI effort field as equivalent. [Nemotron's local API recipe](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-NVFP4) and Laguna document this arrangement. Unknown hosts do not receive the option automatically. GLM-5.3 no longer defaults to an off toggle, following its required-thinking contract. Existing owner overrides remain explicit decisions.

An optional `reasoning_effort_map` translates UI levels to the exact local endpoint contract, for example medium→high and ultra→max when a configured GLM host accepts only low/high/max. This is explicit owner metadata, not a family-name assumption; omit it for hosts whose behavior has not been established. It does not change output/context budgets or override a disabled thinking toggle.

Illustrative existing-profile configuration (replace the provider/model key with the exact ID reported by your server; this audit did not modify owner settings):

```json
{
  "model_capability_profiles": {
    "vllm:poolside/Laguna-XS-2.1": {
      "context_limit": 32768,
      "reasoning_history": "reasoning_content",
      "thinking_control": "chat_template"
    }
  }
}
```

Discovery now excludes GPT-Live and dedicated Gemini transcription, translation and Omni video IDs from the ordinary Chat picker and configuration check. These require specialized routes that this adapter does not implement; conversational Gemini Live remains available. [OpenAI catalog](https://developers.openai.com/api/docs/models/all), [Gemini model catalog](https://ai.google.dev/gemini-api/docs/models).

Compatible native tool streams now require a completed finish reason before returning a tool batch. EOF without completion, or a length-truncated call, raises a provider error and returns no tool calls for execution. Existing Gemini ID/signature and interleaved-fragment fixtures now include proper terminal events. The separate text-call recovery path requires Liquid's explicit closing token; this is not a claim that every compatible stream dialect has been certified.

### Learning, memory and workers

`lean/capabilities.py` describes actual available tools and disabled switches from the live Toolbox, caller role and permissions; it does not negotiate model competence. `lean/personas.py` stores per-agent model choices. `lean/swarm.py` uses bounded read-only workers with the lead's model, not a separate inference provider. `agent/learning/routing.py` is opt-in and uses local outcome evidence, excludes provider/auth/privacy failures from model-quality losses, and restricts auto-selection to owner-listed/allowed models. `lean/memory_quality.py` bounds atomic facts and prompt recall; `lean/summaries.py` summarizes older visible exchanges. None of these components gains access to another provider's opaque state in this change. They also do not prove that a small or unfamiliar model can follow the full prompt/toolset reliably. Keep learning-derived route decisions distinct from official capability metadata.

## Lifecycle, hardware and selection guidance

Refresh IDs from the provider account catalog; use stable snapshots where reproducibility matters. Treat aliases as moving references. Product UI retirement, API deprecation, API shutdown and downloadable historical weights are separate states. The [OpenAI catalog](https://developers.openai.com/api/docs/models/all) labels deprecated/shutdown entries; [Google's catalog](https://ai.google.dev/gemini-api/docs/models) identifies stable/preview/shutdown models; [Cohere](https://docs.cohere.com/v1/docs/models) marks older Command R IDs deprecated. Mistral's historical section does not by itself prove a shutdown. Account discovery can omit gated models or include specialized endpoints; neither outcome certifies native tool compatibility.

An analytical weight floor is `total_parameters × bits_per_weight / 8` bytes. At nominal 4-bit precision, 3B/8B/14B/27B/70B require about 1.5/4/7/13.5/35 GB **before** quantization metadata, non-quantized layers, runtime buffers, visual/audio components and KV cache. These are arithmetic floors, not measured fit recommendations. Hybrid/MoE models still need total selected weights resident or offloaded; active parameter count describes compute, not full memory demand. CPU offload may fit a model with substantially different latency. Long context and parallel sessions increase memory consumption independently of file size.

Consumer candidates include appropriately supported small Gemma, Qwen, Granite, SmolLM and Phi variants. Pick the exact instruct checkpoint, quant and runtime together. Larger 27B/31B dense or 80B MoE allocations require explicit memory planning; frontier Muse/Kimi/DeepSeek/Nemotron allocations generally belong to server or large unified-memory configurations. No throughput, quality ranking, RAM-fit guarantee or GPU purchase recommendation was measured here. Check license, architecture support and projector packaging for the exact artifact; open weights do not imply identical redistribution/commercial rights.

## Remaining work and owner acceptance

Direct DeepSeek, Qwen Cloud, Mistral, Z.ai, Kimi, MiniMax, Cohere, NIM and cloud-hosting accounts are not native provider implementations. Adding arbitrary compatible endpoints needs credential handling, privacy classification, per-provider metadata, protocol state and precise errors—not just a new logo. Grok's current Responses/effort path is a separate follow-up, along with authenticated local endpoints and richer `/api/show` discovery. Local reasoning replay is now available through an explicit exact-model profile; it is not enabled globally or treated as a complete direct-provider integration. The [Kimi K3 card](https://huggingface.co/moonshotai/Kimi-K3) and [DeepSeek thinking guide](https://api-docs.deepseek.com/guides/thinking_mode/) establish why visible reasoning text alone is insufficient.

Capability profiles and family diagnostics still contain permissive/unmeasured defaults. They are not a negotiated serving contract and should not be presented as a successful generation test. Exact context metadata is not yet automatically propagated from every discovery source. Reasoning data retained inside a current Responses turn is discarded when that turn is reconstructed from the timeline, favoring bounded native state over a new persistent opaque store. Long-running and interrupted provider acceptance remains unverified.

High-value manual checks, to be performed by the owner when desired:

1. One GPT-6 API model: a harmless file read followed by a response; then Stop mid-stream, and switch models between turns. Confirm no duplicate action and the intended model label.
2. One current Claude model: change low/high effort, read an image if supported, and complete a permitted tool cycle. Check that denied actions remain denied.

4. One familiar local Gemma/Qwen instruct model on the currently installed server: native tools, a malformed argument, and a deliberately small configured context. Coder-Next should not show automatic thinking controls.
5. Private/Offline mode: verify a remote model is blocked and local work still obeys project scope. Original Codex/Claude/ACP sessions have separate acceptance requirements.

These are focused contract scenarios, not an exhaustive model campaign. Do not select a paid generation check unless you intend to make a real model request.
