1 · The recent failures were one problem

The harness always knew what happened to each call. A policy deny, your "no", an autonomous hold, a switched-off tool: then it wrote that down as a sentence. The refusal breaker, learning and the claim checks each re-guessed it by matching phrases, and nothing checked whether a reported change actually happened.

2 · Four stages of a call, and who fills each

A reported write that isn't on disk is now a failure, with a note to the model. A click that changed under 0.5% of the screen is no_effect. Its row reads "No visible change on screen", and "the Start menu has opened" is challenged.

3 · Where an action can go, and what guards each way out

Before, a command asked when the model chose where="host", but ran unasked when Auto silently fell back to this PC because Docker was down. The boundary now follows the destination. Your "Always allow ordinary commands on this PC" grant and Autonomous mode still cover it, and choosing This PC explicitly keeps the old behaviour.

5 · Kept, changed, and next

kept
  • Deterministic gates; no LLM approver
  • Capability report from code
  • Learning from tool records, holdout-tested
  • Local-first, owner-set autonomy
changed
  • One outcome per call, set where it's decided
  • Effects observed on disk, in exit codes, on screen
  • Refusals, claims and learning read the record
  • Host fallback asks like any host command
next (speculative)
  • UIA precondition check before a click
  • Launch effects for open_application
  • MCP structured results as effects
  • Per-destination egress for the sandbox
  • Windows OS sandbox or WSL2
