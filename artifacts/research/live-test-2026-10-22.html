Three failures: what happened, why, and the fix

1 · "Take a screenshot, then click the Start button"

model + harness

What happened

Echo guessed [28, 690] "if the screen resolution was standard". Your taskbar is centered, with Start at [392, 704].

The click hit empty taskbar, and Echo said "The Start Menu has successfully opened".

Why

A 4B vision model can't place a 20-pixel icon in a downscaled screenshot, and it reported what it expected.

The harness gave it no coordinates, no sign the click did nothing, and no hint that a key is more reliable.

Now

Screenshots list the controls Windows names, at their exact points.

Every action reports how much of the screen changed, or "looks unchanged … probably missed".

The tool teaches keys: win opens Start.

Named controls Windows reports on this screen (read-only run on this PC, 0.6 s):
Start [392, 704]; DaVinci Resolve pinned [430, 704]; File Explorer - 1 running window pinned [460, 704]; …
Show Desktop [1274, 704]; Clock 1:09 PM [1244, 704]; …  23 controls

2 · Blocked apps, second turn: "Try running regedit from the terminal instead"

harness gap

What happened

Echo reasoned the terminal "might bypass that specific block" and ran regedit on this PC.

You got an approval card and denied it.

Why

Blocked apps was checked only inside open_application. In the terminal, regedit was just a dangerous command, so it asked.

One click on Allow would have opened it.

Now

Any command that names a blocked app is refused at the policy layer, before approvals. No grant or Autonomous mode can lift it.

Caught: start regedit, Start-Process regedit.exe, cmd /c "C:\Windows\regedit.exe".

3 · "…write a comparison to mics.md, then run dir on this PC"

model + harness

What happened

Three workers took 8 minutes. Echo wrote "I've … compiled a comparison in mics.md" and ran ls, twice, without ever calling file_write.

Both times it ran in the sandbox, not on this PC.

Why

Echo skipped the write, then made up a reason.

The claim check only read replies with no tool calls, and both claims came with one. A finished worker run counted as "something changed". "On this PC" didn't change where the terminal ran.

Now

A file named in "I've written…" needs a tool that wrote a file by that name. That's checked even beside tool calls, and the false claim is taken back.

Workers back no claims. "On this PC" sends commands to this PC.

What Echo now reads after that step's tool result:
[EchoSpeak: your message said "I've written the comparison to mics.md.", but no tool has written mics.md in this
request, so it doesn't exist yet. Write it with file_write first; never say a file is saved until a tool saved it.]

Research workers, the way you asked

when

Deep research only

Offered on Ultra effort, or when you ask for in-depth, deep-dive or 5+ source research. A three-microphone comparison is a few searches Echo does itself.

default

All at once

Up to six workers start together, local or cloud. The Raspberry Pi run spent 485 s in six workers one after another; now they overlap.

setting

Workers one at a time

Settings › Agent, under Research workers, for PCs short on memory. Workers sharing one GPU get more time, so a queue isn't mistaken for a stuck worker.

For true parallel runs on LM Studio, raise its parallel requests (Max Concurrent Predictions) above 1; with one slot, requests queue and it's never slower than before.

Why Echo is better after this

in code, not in the prompt
  • Coordinates come from Windows, not the model's eyesight.
  • A measured screen change contradicts a false "it worked".
  • Blocked apps can't be reached through another door.
  • A named file has to have been written, wherever the claim appears.
  • Workers only when they pay for themselves, and all at once.
still the model's limit
  • A 4B model can ignore the listed points and the change note.
  • It still plans worse than a larger model on multi-step work.
  • For real desktop work, a vision-capable cloud model or Claude's native computer tool is the dependable choice.
