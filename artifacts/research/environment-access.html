Where a read goes now

Decided in trusted code before the call, then checked again at the tool boundary. Nothing the model writes can grant access.

A grant never opens writing: editing still needs an attached project. Channels and unattended routines are told how access is given, but never use a grant made on a card in the app.

What the trails showed

Baseline: the boundary was one tool wide

After file_read was refused, Qwen ran cp and cat of the same file in the sandboxed terminal (which mounts / read-only) and answered from it. The owner was never asked.

Now: asked, then honoured

Every outside read went to the card. After a "No", Qwen tried file_list on the folder; it was refused without a second card, and the reply said the owner had declined.

Still open

EchoSpeak itself prefetches its GitHub pulls and releases pages when a message mentions "echospeak" (here inside a path) and "release": 2 wasted calls per run. It was first written up as model behaviour; it is the harness. And in 1 of 3 runs Qwen asked in prose instead of raising the card (model behaviour).

Credentials, before the fix

With the file root at the home folder (the default when ~/Documents is missing), file_read("~/.ssh/id_ed25519") returned the key. bubblewrap already hid it from commands. A failing test showed it first; file tools now hide the same places as the sandbox.
