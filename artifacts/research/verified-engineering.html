Six stages, one loop, no new engine

The stages are a workflow inside Echo's existing loop, not six model calls. Each maps onto a part that already existed. The one new piece is a deterministic ledger that watches what runs.

Objectiveset_objective: criteria, the check, an optional metric with a direction and target
ResearchCode reads, search and sources (11.11.3), as before
EnvironmentMissing packages, programs, permissions and services recognised as the setup's fault
VerificationTest, build, type, lint and benchmark output parsed into counts, failing tests and the first error
AdaptationProgress against the best result, regressions, stalls and the bottleneck, on each check's result
CompletionA status computed from evidence, under the answer, in the work record and the episode

Chat stays light: no ledger, no set_objective. Codex, Claude Code and ACP keep their own loops; nothing in them changed.

Hill climbing, bounded

What the model sees after a check

Before

[exit code 1 · 0.4s · sandbox · /w] FAILED tests/test_dates.py::test_leap_year - AssertionError E assert 28 == 29 1 failed, 4 passed in 0.21s

Raw output only. A failing run still cleared "check before you say it's done", so "All tests pass now!" went through.

Now

[exit code 1 · 0.4s · sandbox · /w] … 1 failed, 4 passed in 0.21sVerification, before any change: test `pytest -q tests/test_dates.py`: 1 failed, 4 passed, exit 1. Progress: first run of this check (the baseline). Failing: tests/test_dates.py::test_leap_year. First error: assert 28 == 29 Fix the implementation for these failures; don't change the tests to make them pass.

The same result, plus a structured record as an app note. No extra model call: the write, test, answer run is still exactly 3 calls.

Later checks add: improved on, or worse than, the best result (naming the step and how many file changes back it is), the baseline, the target status and the bottleneck with its next action.

"All tests pass" over a red run

Sent back once with the evidence, as an app note, never as you. If the claim stands, the note says what the evidence shows, and the episode is recorded as a false success.

The best result is never hidden

A worse final state still reports "best was step N". Interrupted work saves the whole ledger, and the resumed attempt re-runs the check and compares with the earlier baseline.

Learning counts what the strategy caused

Counts as a win

  • effective: checked and it worked
  • confirmed by you

Counts as a loss

  • checks still failing
  • false success: said done, but the evidence disagrees
  • the last action failed, or it stalled
  • verifier gap: checks passed, but you said it didn't work

Never counted

  • environment, authorization
  • a tool that broke, a model outage
  • information it couldn't find
  • you said it misunderstood

Your feedback reclassifies

"The file was generated, but it doesn't open in Excel" on a checked task is a verifier gap: a loss, and worth learning a better check from. "You misunderstood, I meant…" takes the blame off the lessons, and nothing is learned from it. The note is never turned into an instruction.

Is it helping?

Verified completion, false success, recovery, stalls, attempts and tokens per verified task, and each lesson against its random holdout: helps, no effect, or negative transfer. From GET /lean/learning/evaluation.
